# Phase 7 — Archetype Container Protocol

## Purpose

Select the structural carrier that can preserve and express an existing Edge Product.

## Decision law

The selector MUST NOT ask “Which archetype performs best?” in isolation.
It MUST ask:

> Which canonical structural grammar can carry this specific Edge Product, under this audience state, guest alignment, maturity, and Director intent, while preserving its semantic force?

## Eligibility dimensions

1. Edge preservation
2. Structural capacity
3. Archetype invariants
4. Representation compatibility
5. Audience capacity/maturity
6. State compatibility
7. Routeability
8. Anti-centroid profile
9. Director-note compatibility
10. Historical benchmark as tie-breaker, not authority

## Selection procedure

```text
retrieve candidate archetypes
→ schema link relevant contracts
→ eliminate structurally incompatible carriers
→ evaluate semantic preservation
→ evaluate state/maturity compatibility
→ evaluate routeability
→ compare anti-centroid failure surfaces
→ select sparse shortlist
→ bind highest-ranked admissible container
→ record rejected alternatives
```

## Structural invariants

Every archetype definition must specify:
- intent
- activation conditions
- required phase/order logic
- invariant beats or slots
- admissible variation
- forbidden structural distortions
- compatible SFL families
- expected anti-draft profile

## Important distinction

`ArchetypeContainerDefinition` is reusable and canonical.
`ArchetypeContainerSelection` is contextual.
`ArchetypeInstance` belongs downstream to concrete content realization.

## Prohibited shortcuts

- format-first selection
- “viral format” as sufficient reason
- style imitation as archetype selection
- changing an archetype definition to make a single Edge fit
- letting historical performance override semantic incompatibility
