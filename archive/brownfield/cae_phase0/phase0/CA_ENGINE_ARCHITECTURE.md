# 1. Purpose

This document defines the canonical architecture of the Conscious Activation Engine (CAE), a brownfield evolution of the existing Conscious Activation / CCP codebase.

The engine is not a generic content generator. It is a human-first intelligence and editing system that converts reality-grounded human evidence into structured semantic programs, compositional plans, executable media instructions, and measurable outcomes.

The system's constitutional causal chain is:

`WORLD → CONTEXT/STATE → RELATIONAL INTELLIGENCE → ACTIVE PRESSURE → PROVOCATION → HUMAN RESPONSE → AUTHENTICATED EVIDENCE → TRANSFORMATION → COMPOSITION → REALIZATION → RUNTIME → OUTCOME → MEMORY`

The engine is therefore best understood as an **upstream intelligence + semantic compilation + media realization system**.

# 2. Core Constitutional Principles

## 2.1 Human-first evidence law

The engine shall prefer authenticated human expression over synthetic invention whenever a task is intended to derive guest-specific meaning.

**No authenticated response, no earned downstream rendering.**

A research hypothesis may generate a provocation. It may not masquerade as authenticated guest evidence.

## 2.2 Role-before-schema law

No schema shall be designed before the architectural role of the object has been established.

The question is first:

> What kind of thing is this and what job does it perform?

Only then:

> How should it be represented?

## 2.3 Canonical / dynamic / evidence / derived separation

The engine shall distinguish at minimum:

- **Canonical:** relatively stable definitions, ontology, taxonomy, registries, contracts.
- **Dynamic:** states, activations, current tensions, coalition weights, contextual conditions.
- **Immutable Evidence:** transcripts, source citations, original visual specimens, director notes, source media.
- **Derived Artifacts:** inferred schema, edge products, semantic programs, composition IR, hypotheses.
- **Events:** timestamped observations or actions.
- **Receipts:** execution traces proving what the system did and why.

No derived artifact shall silently overwrite immutable evidence.

## 2.4 Multi-language engineering law

The architecture supports multiple representations for different jobs:

`Human prose → semantic interpretation → typed object → canonical schema → validated program → IR → runtime`

Prose is legitimate source material. It is not the default database schema.

## 2.5 Anti-centroid law

The engine shall actively resist statistical mean-reversion, generic corporate language, unnecessary sanitization, and loss of meaningful tension.

Governance exists to preserve specificity and edge, not to flatten it.

## 2.6 Constraint ≠ censorship

A constraint is legitimate when it preserves a declared architectural property, source truth, or execution contract. It shall not introduce generic moralizing, unnecessary permission language, or stylistic sterilization.

## 2.7 Reality-contact law

Architectural conclusions must remain traceable to source evidence, current codebase behavior, explicit hypotheses, or documented research. Unsupported assumptions shall be marked as hypotheses rather than silently promoted to facts.

# 5. Data Architecture

The logical schema is language-independent. PostgreSQL, JSONB, vector stores, typed models, views, functions, and event tables are implementation mechanisms.

```text
Logical schema
  ↓
PostgreSQL relational tables
  + JSONB for evolving structures
  + vector indexes for semantic retrieval
  + graph-like relations / recursive queries
  + Pydantic / SQLModel / Zod at program boundaries
  + views / functions for governed agent access
  + event tables for temporal history
```

Stable semantics should prefer typed columns and explicit relations. Evolving or exploratory attributes may use JSONB. Evidence should remain immutable. Vector retrieval shall augment, not replace, canonical relations.

# 6. Agent Governance Model

Agents shall not be given an undifferentiated semantic universe when the task can be expressed as a structured state-space query.

Preferred execution pattern:

`Human Intent → Schema Linking → Relevant Entities/Relations → Subproblem Decomposition → Retrieval/Composition Plan → Structured Query → Execute → Validate → Typed Error → Repair`

Database access for agents should normally occur through authorized views, functions, procedures, and typed service boundaries rather than unrestricted database access.

# 7. Editing as the General Operation

Editing is the cross-layer operation of the engine:

`selection + exclusion + combination + ordering + emphasis + preservation`

It occurs in:

- Audience intelligence
- Guest intelligence
- Context interpretation
- Tension selection
- Primitive candidate selection
- Coalition formation
- Archetype selection
- Scene composition
- Visual editing
- Runtime rendering

The engine is therefore fundamentally a system for **organizing and distilling intelligence for meaningful reasons**.

# 8. Brownfield Doctrine

Every implementation decision shall first classify existing behavior as:

- `EXISTS`
- `PARTIAL`
- `DUPLICATED`
- `CONFLICTING`
- `SPEC_ONLY`
- `MISSING`
- `DEPRECATED`

No new component should be built merely because it is absent from a current mental model. The codebase must be inspected before requesting human decisions that code can answer.

# 9. Source-of-Truth Hierarchy

When sources disagree, apply the authority model defined by the Canonical Architecture Laws document and record the conflict in the Architecture Decision Ledger.

No historical document is silently authoritative merely because it is older or more detailed.

# 10. Non-Goals

This architecture does not require:

- one universal schema for every object
- one universal registry for every artifact class
- replacing evidence with vector similarity
- replacing human judgment with automated authorization bureaucracy
- treating biological language as scientific fact
- treating hypotheses as established evidence
