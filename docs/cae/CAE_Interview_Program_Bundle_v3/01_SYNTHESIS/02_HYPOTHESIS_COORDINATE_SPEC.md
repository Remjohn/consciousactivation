# Hypothesis Coordinate & Collision Specification

**Status:** BUNDLE-PROVISIONAL
**Canonical objects introduced:** none

## 1. Purpose

Define how upstream intelligence can produce candidate interview/content hypotheses without inventing a parallel `ContentHypothesis` ontology.

## 2. Coordinate basis

The provisional coordinate basis is:

| Dimension | Meaning |
|---|---|
| D01 Audience tension | active pressure or unresolved audience condition |
| D02 Audience belief | relevant belief/schema/cognitive island currently organizing the issue |
| D03 Audience desired state | desired recognition, movement, relief, or capability |
| D04 Guest lived authority | lived territory from which the Guest has legitimate evidence |
| D05 Guest contradiction | tension between current/former stance, behavior, identity, or evidence |
| D06 Guest transformation | meaningful change across time or context |
| D07 Cultural/world signal | current external signal, research, event, discourse, or environmental change |
| D08 Target enemy/status quo | paradigm, assumption, system, or default interpretation under pressure |
| D09 Oblique lens | non-obvious comparison, metaphor, adjacent knowledge, or cross-domain lens |
| D10 Archetype opportunity | plausible downstream content archetype(s) |
| D11 Distribution condition | relevant syntax/distribution condition without allowing performance to override semantic quality |
| D12 Evidence opportunity | specific evidence that could resolve or enrich the collision |

These are coordinates, not content categories. Their final authoritative definition must be reconciled against existing CAE objects/registries before implementation.

## 3. Guest Workspace state

Each relevant coordinate may have derived state such as:

- value;
- confidence;
- evidence density;
- recency;
- recent activation;
- historical performance reference;
- provenance;
- applicable audience cognitive-island reference.

Do not create a new persistent canonical object for this merely to satisfy the Interview Program.

## 4. Collision formation

Candidate generation is conceptually:

`current audience cognitive islands`
`+ guest semantic territory`
`+ world/research signals`
`+ active edge`
`+ format/archetype intent`
`→ candidate collision`
`→ testable hypothesis instance`

The collision must state what is being tested, what evidence would strengthen/contradict it, and why the Guest is a relevant source of evidence.

## 5. Hypothesis fields (derived adapter)

A candidate instance should be able to carry:

- upstream activation-hypothesis reference(s), when available;
- coordinate references/values;
- collision statement;
- target audience cognitive island;
- target Guest territory;
- edge/tension reference;
- target paradigm/enemy;
- expected discrepancy/contradiction;
- desired evidence;
- question objective;
- question mechanism coalition reference(s), if known;
- archetype candidates;
- format candidates;
- distribution hypothesis, when appropriate;
- confidence and provenance;
- selection diagnostics.

This structure is an **adapter/view/derived representation** unless and until the repository constitution declares otherwise.

## 6. Candidate volume

`~96` is an operational search/portfolio target. It is not a schema cardinality, ontology cardinality, or production requirement.

Candidate generation may produce fewer when source density is low, and more may be temporarily evaluated internally. The user-facing target of approximately 96 must not become a brittle hard requirement.

## 7. Diversity principle

Selection must maximize useful semantic diversity, not raw score. Diversity dimensions can include:

- audience cognitive island;
- tension;
- guest territory;
- time orientation;
- archetype;
- evidence mode;
- world signal;
- contradiction pattern.

Duplicate or near-duplicate hypotheses must incur a portfolio penalty or be clustered before final selection.
