# 15. Operator Application, Production Control Surface & Runtime Convergence

The Operator application is not a dashboard placed on top of CAE. It is the **control surface through which human authority is exercised over the canonical production runtime**. This distinction determines the product architecture. The UI may organize information, accelerate decisions, and expose rich visual context, but it must not become a second execution engine with its own hidden state, business rules, or approval semantics.

CAE therefore requires **runtime convergence**: every production surface must converge on the same authoritative program state, contracts, identifiers, transitions, and receipts. The repository's top-level organization reflects this direction. The web application is separated from the API and from the service packages, while shared packages provide canonical contracts and runtime helpers; the service layer contains dedicated domains for pipeline, interview, outcome, operator intelligence, VAE, asset intelligence, and related work. The primary user remains the **Operator**. The Operator manages multiple Leader workspaces, coordinates interviews, inspects evidence, resolves recommendations, handles exceptions, and authorizes irreversible transitions. CAE should make this human work faster without pretending that the Operator is an obsolete approval bottleneck. The application is successful when an Operator can understand what the system is asking, why it is asking it, what evidence supports the recommendation, and what will happen if they accept or reject it.

The control surface should expose the production state in terms of work rather than infrastructure. Instead of requiring the Operator to understand microservices, the UI should organize the workflow around concepts such as **Campaign, Subject, Narrative Plan, PreProduction Plan, Interview, Evidence, Candidates, Storyboard, Composition, Render, QA, Approval, Release, and Outcome**. These objects map to the causal chain established elsewhere in the Product Brief and provide stable locations for human decisions.

The Operator needs different modes of interaction. **DISCOVER** and **INSPECT** support understanding. **RUN** launches declared work. **PAUSE** and **RESUME** manage long-running or blocked execution. **APPROVE**, **REJECT**, and **REPAIR** express human decisions. **SHIP** advances a package toward final release when all gates pass. **EXPORT_AUDIT** exposes the evidence needed for forensic review. These are not decorative buttons; they are the UI representation of typed runtime actions.

Authority lanes also need to remain visible enough to be meaningful. Hunter, Analyst, Composer, and Commander represent different cognitive jobs inside the production system. The interface should preserve their distinction without forcing the Operator to think in internal software architecture. A Hunter candidate should feel like a discovery object. An Analyst result should feel like an interpretation or ranking. A Composer object should expose the evidence and contract it is assembling. A Commander decision should be where consequential state transition occurs.

The control surface must also protect the Operator from stale state. Approval is meaningful only relative to the object that was inspected. The runtime's state-version and state-hash approach is therefore important: an approval should fail or require reinspection if the object changed between review and authorization. This prevents a common class of distributed UI bugs in which the interface appears to approve one version while the backend applies the action to another.

Chat interfaces should be treated as adapters, not alternative products. A Slack or Telegram message can notify an Operator that an interview is ready, ask for a simple disposition, or communicate an exception. A richer Mini App can open when a video or asset needs visual inspection. But these channels must call the same canonical runtime and receive the same authoritative state. A “yes” sent from chat should be the same governed approval action as a click in the web console, not a separate interpretation path that produces an approximate state change.

This becomes especially important for natural-language interaction. Operators will inevitably type statements such as “this is too generic,” “use the earlier quote,” or “find a stronger visual.” The application can use intelligence to translate these utterances into structured corrections, but the final operation must still map to a typed runtime command. Natural language is an input modality, not an authority system. This keeps convenience from eroding governance.

The UI should also expose **evidence before polish**. When reviewing a candidate artifact, the Operator should be able to inspect the source transcript or media span, the selected evidence, the narrative purpose, the composition lane, any synthetic bridge, and the validation state. A beautiful preview without evidence context encourages aesthetic approval. CAE requires semantic approval first and visual approval second where the product contract demands both.

Runtime convergence also applies to errors. If the backend blocks an artifact because provenance is incomplete, the UI should not reinterpret that state as “AI had trouble.” It should explain the contract failure and present only permitted next actions: retrieve more evidence, repair the source, change the format within a valid mode contract, request another model pass, or accept a yield shortfall. This makes fail-closed behavior operationally useful rather than frustrating.

The Operator application should therefore be designed around **decision latency**, not click volume. A good interface compresses the cognitive work needed to inspect evidence, understand a proposal, and make a governed decision. This can include side-by-side transcript and artifact views, collision explanations, asset previews, provenance overlays, approval checklists, and visible exception reasons. Automation should remove repetitive navigation and data handling, not remove the information needed for a high-quality human decision.

The architecture should also support progressive disclosure. Expert Operators may want complete lineage, model invocation details, and audit records. Routine work should present a simpler path. The same underlying object can serve both levels without duplicating state. This is another benefit of canonical runtime convergence: richer views are presentation choices, not separate data models.

The most important product invariant is:

> **One program state, many interaction surfaces.**

There is one campaign state, one authority model, one provenance chain, one release state, and one canonical production history. The web app is not allowed to become the “real” system simply because it has the richest UI. Likewise, a chat integration is not allowed to become a shadow controller because it is convenient. All roads lead to the same runtime.

This gives CAE a durable way to evolve. New channels can be added without rewriting production logic. New visual inspection tools can be introduced without changing artifact semantics. A mobile surface can eventually expose the same work objects without creating a mobile-specific campaign state. The runtime remains the source of truth, while the application becomes an increasingly effective human control surface over that truth.

The end state is not a dashboard that happens to trigger AI. It is a **production operating console for a governed evidence transformation engine**. The Operator sees what matters, the runtime enforces what is allowed, and every action converges on the same state graph. That is the architecture required to scale human judgment across a portfolio without multiplying operational ambiguity.
