# CAE-BMAD Upstream Policy and Equivalence Contract

**Version:** 0.3.0-rebuild  
**Status:** CANONICAL POLICY  
**Authority:** CAE Rebuild Program / Operator Mandate M01  
**Scope:** Policy for preserving original BMAD capabilities, specializing workflows, and preventing destructive overrides.

---

## 1. Lineage and Repository Grounding

CAE-BMAD is an agile product-development method derived from the Remjohn BMAD fork (`https://github.com/Remjohn/BMAD-METHOD`) and specialized for the Conscious Activation Engine brownfield environment.

Upstream BMAD provides:
- Durable progressive artifact flow (Brief → PRD → Architecture → Epics/Stories → Implementation).
- Core skill interfaces (`bmad-help`, `bmad-review`, `bmad-deep-recon`).
- Collaborative role personas and modular planning templates.

CAE-BMAD provides:
- The 13-level bidirectional engineering operating model.
- The 216-source research reconstruction protocol.
- The single-question, evidence-first CAE Grill gate.
- Deep brownfield reality mapping into existing Python, TypeScript, and database runtimes.
- Strict anti-false-proof standards and operator gate governance.

## 3. Upstream Preservation Invariants

1. **Non-Destructive Specialization:** Under no circumstances should original BMAD capabilities be deleted or truncated into hollow stubs. Every CAE equivalent must provide equal or greater analytical depth.
2. **Runtime Separation:** CAE-BMAD method tools must never overwrite existing application runtime primitives (`services/`, `packages/`, `programs/`) unless executing a formally planned and operator-approved migration mandate.
